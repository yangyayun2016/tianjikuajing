## 可迁移实践

### 1. 约 30x 发码，前提是"agent-friendly 架构"

她在 2026-11-04/05 的更新里提到：团队拿到大约 **30x 的发码量**，人不再逐行读代码，而性能没有掉；同时要"驯服 slop"；10 月约有 **230 人**给 Grok Bot 合过 PR。

这组事实容易被误读成"上 agent 就能 30x"。真正的因果是反的：

- 先把**环境、类型、检查、目录结构**改到 agent 能自己跑通，速度才出现；

- 人从"逐行审代码"退到"审接口、审边界、审结果"；

- 没有确定性检查兜底，30x 只会变成 30x 的技术债。

对应到我们：**先修跑道，再放飞机。** 广告健康规则、打标本体、字段字典要先写进 skill / 仓库，再谈扩 bot 数量。

### 2. `/statechart`：先画状态机，再让 agent 动手

新加的 `/statechart`（配合 TLA+）用法很朴素：**站在用户视角画出状态图，用它核对 agent 到底有没有理解目标**。

agent 最常见的失败不是"不会写"，而是"目标理解偏了还写得很顺"。状态图是低成本的照妖镜：

- 状态有哪些、谁能迁移、哪些迁移不可逆；

- 哪些事件必须先有数据、哪些必须先有人批；

- 出错时应该退到哪个状态。

所以我们在做广告健康巡检、关键词打标流水线之前，应该先画状态机，而不是先写 prompt。

### 3. 别让自己当瓶颈

她的原话意思是：多任务并行时，**不要先去开新 UI**，先看看自己是不是卡住了整条链路。

团队里最贵的瓶颈往往不是模型，而是"只有某个人能批、只有某个人知道口径、只有某个人能发版"。可操作的做法：

- 审批门只拦**高风险**动作，低风险的先放行；

- 把"我知道但没写下来"的东西固化成 skill / 规则 / 字段定义；

- 能自动回读验证的，不要排人工 review 队列。

### 4. `/automate-me`：fork `poteto-mode`，做自己的 Bot 工厂

她的做法是把自己的工作方式做成可 fork 的模式（`poteto-mode`），再用插件扩展出 `eggbot`、`tinkabot` 这类专岗 bot。

这背后的判断是：**bot 不该是一个万能助手，而应该是一条能复制岗位的生产线。** 一个岗位跑通 → 打包成 skill/插件 → fork 出下一个岗位。

### 5. 合并前 agent 自检，不再只靠传统 CI

最新的做法是：**在合并前让 agent 自己完成一轮自检**，而不是把全部信任压在传统 CI 上。

这不是"取消 CI"，而是分工变化：

- 传统 CI 管**确定性**：类型、lint、单测、构建；

- agent 自检管**语义**：改动是否真的解决了问题、有没有越权、有没有偷偷改口径、边界情况有没有覆盖；

- 人只看自检结论 + 高风险点。

多轮 agent review 会把 PR "overcook"（越改越肿），所以她的偏好是**少一点对抗式抽象 review，多一点实测和确定性检查**。

### 6. pstack 的日常口令

`/setup-pstack`、`/poteto-mode`、`/correct`、`/architect`、`/in-your-own-words`。

其中两个最值得抄：

- **`/correct`**：每次纠正 agent，不是聊完就完，而是把纠正沉淀成规则；

- **`/in-your-own-words`**：让 agent 用自己的话复述任务，暴露理解偏差——这和 `/statechart` 是同一套思路的两种粒度。

### 7. First mile / Last mile 与闭环

- **First mile**：先把日历、CRM、Slack、邮件这些入口接上，让 bot 有真实输入；

- **Last mile**：复杂改仓交给 Cursor 云端写码；

- **闭环 Loop**：盯频道 → 进 Linear → 云端复现 → 小群 fuzz → Slack 通知 / 自动合并。

闭环的关键不是自动化率，而是**每一环都有回读**：改完要看报表、看日志、看真实频道里的反馈。

## 架构纠正优先级

这是整份笔记里最该被贴到墙上的四行：

```
更好的架构 / 数据结构  >  lint、测试进 CI  >  skill / rule  >  纯靠人审
```

含义很直接：

1. 同一个错误反复出现，先怀疑**数据结构或架构**错了，别急着加规则；

1. 架构一时改不动，就把检查**前移到 CI**，让机器每次都拦；

1. 再不行，写成 **skill / rule**，至少让 agent 每次都读到；

1. **纯靠人审是最后一道，也是最贵、最不可靠的一道。**

我们常见的反模式正好倒过来：出了事故 → 加一条"请人工确认"→ 人越来越忙 → 真正的架构问题一直没动。

## 对天机跨境 SI Bot 的落地建议

前提：我们的 SI Bot 已经有 `rolespecs/*.yaml`（一岗一责、固定交付、权限 P0–P5、红线、高风险须 Boss 批），也有 ads-advisor、关键词打标、店铺健康、VOC 等岗位骨架。所以不需要"再上一个 agent 平台"，而是把这套方法**灌进现有骨架**。

**第一周：只做三件低成本的事**

1. **给两条流水线补状态图。** 广告健康巡检、关键词打标各画一张用户视角状态机（正常 → 告警 → 待诊断 → 已提审 → 已执行 / 已回滚），贴进对应 `rolespecs`，作为 agent 的验收依据。这就是 `/statechart` 的最小可用版。

1. **把口径从人脑搬进仓库。** 字段字典、ABA 口径、健康阈值、打标规则写进 skill 与 rules 目录；每次人工纠错，走一遍 `/correct` 的流程沉淀成规则，而不是在群里说一遍。

1. **审一遍审批门。** 对照"别让自己当瓶颈"：确认 P3/P4 只拦对外发送、动资金、承诺交付、删除数据这类不可逆动作；低风险查询与分析默认放行，否则 Boss 一定会变成瓶颈。

**第二到四周：把"自检"接到合并前**

1. **双层验收。** 确定性层：schema 校验、规则引擎回读、报表比对（对应"信实测"）；语义层：agent 自检清单——是否越权、是否编造数据、是否改了口径、结论是否有来源。两者都过才允许进入 `approved_simulation` → 人工批准。

1. **禁止多轮 overcook。** 一个 PR 超过两轮 agent 互审就停下来，改成用一条真实数据回读验证，避免为了"更严谨"把改动堆成不可维护的坨。

1. **回读优先于 review 意见。** 广告类结论以报表回读与规则引擎结果为准，不以"reviewer 觉得对"为准。

**月度：把岗位做成可 fork 的生产线**

1. **复制岗位而不是复制 prompt。** 选一个已经跑顺的岗位（建议从店铺健康巡检或 VOC 开始），把它打包成「RoleSpec + skill + 插件 + 固定交付模板」，再 fork 出相邻岗位。这就是 `/automate-me` 在我们场景下的翻译。

1. **先接 First mile。** 飞书/Slack 频道、周报、工单入口先打通，让 bot 有真实输入流；复杂改仓再交给云端编码 agent，别让 bot 在真空里编数据。

1. **扩规模前先看架构债。** 想从 3 个 bot 扩到 10 个之前，先回答：类型/契约是否齐全？检查是否进了 CI？口径是否只在某个人脑子里？三个都是"否"的话，扩出来只会是 10 个各自编数据的 bot。

**一句话红线（沿用现有制度）**：agent 提速的前提是**可追溯 + 可回读 + 高风险必须人批**。30x 的前提是架构友好，不是胆子大。

## 一句话总结

@poteto 这一轮更新真正在讲的不是"agent 多能干"，而是：**把架构、类型、状态机、规则这些"环境"修好，人退出逐行审查，只保留高风险决策权**——然后速度会自己出现。
