# 2. Dify 应用类型

        Dify 平台提供了**可视化、低代码**的应用创建体系，针对不同业务场景与交互需求，设计了差异化的应用类型，涵盖自动化任务、多轮对话、智能推理、文本生成等核心场景。在「创建空白应用」模块中，可根据业务逻辑复杂度、交互形式选择对应类型，各类型在编排逻辑、交互能力、适用场景上存在明确区分，其中**工作流（Workflow）** 与**Chatflow** 是平台核心的流程编排型应用，也是企业级场景的核心选型，以下结合平台界面与功能特性展开详细介绍。

![](assets/%E5%A4%A9%E6%9C%BA%E8%B7%A8%E5%A2%83%E6%B2%99%E9%BE%99Dify%E5%9F%B9%E8%AE%AD%E8%B5%84%E6%96%99_WaK8bJGd8o.jpg)

## 2.1 工作流（Workflow）

### 定位与核心定义

        工作流是 Dify 面向**单轮自动化任务**设计的流程编排型应用，核心聚焦**无交互、一次性、流程化**的自动化任务处理，无需用户参与多轮对话交互，仅通过可视化节点编排完成数据处理、信息提取、任务执行等全流程自动化操作，是轻量化自动化场景的基础选型。

### 核心特性

1. **单轮任务导向**：仅支持单次任务触发与执行，无对话上下文记忆与多轮交互逻辑，流程执行完成即终止，资源占用低、执行效率高；

1. **可视化流程编排**：基于拖拽式节点编辑器，支持串联 / 并联节点、条件分支、数据流转配置，可快速搭建数据清洗、API 调用、文本处理、批量任务执行等自动化流程；

1. **轻量化执行逻辑**：无需维护对话状态，流程逻辑聚焦任务本身，适配无需人工干预的自动化场景，降低配置复杂度；

1. **全链路数据可控**：支持节点间数据传递、变量定义、结果输出，可精准控制自动化任务的执行链路与输出格式。

### 适用场景

- 批量数据处理（如批量文本摘要、数据格式转换、信息提取）；

- 单轮 API 自动化调用（如第三方接口数据拉取、系统间数据同步）；

- 一次性任务执行（如报告生成、文件处理、规则校验）；

- **无需用户交互的后台自动化流程。**

## 2.2 Chatflow

### 定位与核心定义

Chatflow 是 Dify 基于工作流能力升级的**复杂多轮对话型应用**，是平台针对交互式场景打造的核心产品形态，融合了「流程编排的灵活性」与「多轮对话的交互性」，支持自定义对话逻辑、上下文记忆与复杂交互分支，是智能对话场景的核心解决方案。

### 核心特性

1. **多轮对话与上下文记忆**：内置对话记忆机制，可自动保留用户多轮交互的上下文信息，实现连贯的对话体验，支持上下文变量调用、历史信息引用，完美适配复杂对话场景；

1. **可视化对话流程编排**：延续工作流的拖拽式编排能力，可自定义对话节点、回复节点、条件分支、工具调用节点，灵活配置对话逻辑（如问答分支、意图识别、多轮追问）；

1. **实时预览与调试**：支持对话效果实时预览，可快速调试对话流程、节点配置与回复逻辑，降低对话应用的迭代成本；

1. **流程与交互深度融合**：既具备工作流的自动化处理能力，又支持用户实时交互，可在对话中嵌入数据处理、API 调用、信息查询等流程，实现「交互 + 自动化」的一体化场景。

### 适用场景

- 智能客服（多轮咨询、问题分流、自动回复）；

- 对话式助手（如企业知识库问答、产品咨询助手）；

- 复杂交互场景（如多轮表单收集、任务式对话、智能导购）；

- 需结合流程处理的对话场景（如对话中查询数据库、调用第三方接口）。

## 2.3 其他应用类型

### 聊天助手

         定位为**极简配置的基础对话机器人**，无需复杂流程编排，仅通过简单参数配置（如模型选择、提示词设定、回复规则）即可快速搭建基于大语言模型的轻量化对话应用，核心适配入门级、无复杂逻辑的基础对话场景，是新手快速上手 Dify 对话能力的首选类型。

### Agent节点

         是具备**自主推理与工具调用能力**的高阶智能助手，核心面向复杂决策型场景，支持自主拆解任务、推理执行步骤、联动多工具完成复杂任务，可自主调用平台内置工具 / 第三方工具，实现从任务理解到执行的全流程自主化，适配需要智能决策、多步骤协同的高阶业务场景。**（就是在聊天助手的基础上加了配置工具的能力）**

### 文本生成应用

         是 Dify 针对**纯文本生成任务**专项优化的应用类型，聚焦文案创作、文本改写、摘要生成、内容创作等单一文本处理场景，配置流程简洁，核心围绕文本生成的模型参数、提示词、输出格式进行配置，无需复杂交互与流程编排，专注输出高质量文本内容。

# 3. 工作流节点（chatflow相同）

        工作流（Workflow/Chatflow）是 Dify 实现流程化任务处理与交互式对话的核心载体，而节点则是构成工作流的基础单元，不同节点承担着数据输入、模型调用、内容回复、文件处理、知识查询等差异化功能，通过节点的串联与配置，可实现从简单任务到复杂交互场景的全流程搭建。以下将结合 Dify 平台界面与实际配置逻辑，对核心工作流节点进行详细介绍。

## 3.1 开始节点

         开始节点是 Chatflow 与 Workflow 应用的**必备起始节点**，是整个流程的入口，用于定义流程触发时的输入参数与系统变量，为后续节点执行与数据流转提供初始配置，是搭建工作流的第一步。

### 核心配置项

1. **输入字段**：支持用户自定义文本、数字、文件、文件列表等类型的输入项，可设置是否必填，用于接收用户触发流程时传入的参数（如用户查询内容、上传文件、表单数据等），是流程与外部交互的核心入口。**这里的输入字段不仅是可以用户输入，在对接外部服务始也可以通过相应的变量名进行调用然后来使用工作流。**

1.                                       

![](assets/%E5%A4%A9%E6%9C%BA%E8%B7%A8%E5%A2%83%E6%B2%99%E9%BE%99Dify%E5%9F%B9%E8%AE%AD%E8%B5%84%E6%96%99_TKTrb9l0uo.jpg)

1. 系统变量（内置，无需自己配置）：Dify 为 Chatflow 与 Workflow 预置了标准化系统变量，无需手动配置即可直接调用，涵盖用户信息、会话信息、应用信息、流程信息等维度，核心系统变量及说明如下：
  - **Chatflow 专属系统变量**：`**sys.query**`**（用户对话输入内容）**、`sys.files`（用户上传文件）、`sys.conversation_id`（对话会话 ID）、`sys.user_id`（用户 ID）等，适配多轮对话场景的上下文与用户标识需求。
  - **Workflow 专属系统变量**：`sys.workflow_id`（流程 ID）、`sys.workflow_run_id`（流程执行 ID）、`sys.app_id`（应用 ID）等，适配单轮自动化流程的标识与追溯需求。

**开发注意点：可根据实际场景灵活配置，比如下拉选项、复选框这些字段可以满足那些需要限定用户进行选择或者不同功能策略时来使用。**

### 功能价值

作为流程起点，开始节点实现了 “输入定义 + 变量预置” 的双重能力，既满足自定义参数的灵活配置，又通过系统变量简化了用户、会话、流程等基础信息的调用，确保后续节点能精准获取初始数据，保障流程正常启动与流转。

## 3.2 LLM 节点

LLM 节点是 Chatflow 与 Workflow 的**核心功能节点**，依托大语言模型的自然语言处理能力，实现文本生成、内容理解、逻辑推理、信息提取等核心操作，是工作流实现 AI 能力的关键载体。

### 核心配置项

1. **模型选择**：支持对接 Dify 内置的各类大语言模型（如 DeepSeek、通义千问、GPT 系列等），可根据场景需求选择适配模型，兼顾效果与成本。

1. **（SYSTEM）系统提示词**：用于向模型输入系统提示词，定义模型的角色、任务规则与输出规范（如 “你是专业的业务顾问，需根据用户问题精准解答”），是引导模型输出的核心配置。

1. **用户输入（USER）**：可关联开始节点的输入字段、系统变量或其他节点的输出结果，作为模型的用户侧输入（如用户查询内容、文件提取文本、知识检索结果等），实现数据的动态传入。

1. **视觉 / 文件支持**：部分模型支持视觉能力，可传入图片实现图文理解；同时支持关联文件变量，实现基于文件内容的模型处理。

1. **输出变量**：自定义模型输出的变量名称，便于后续节点调用模型生成的结果；支持异常处理配置，可定义模型调用失败时的回复或流程分支。

![](assets/%E5%A4%A9%E6%9C%BA%E8%B7%A8%E5%A2%83%E6%B2%99%E9%BE%99Dify%E5%9F%B9%E8%AE%AD%E8%B5%84%E6%96%99_E6VmbGlTxo.jpg)

**注意点：知识库需要通过上下文配入，然后在提示词进行导入使用，系统SYSTEM提示词影响程度高于user提示词，更加精细化的场景可点击模型可以调整相应的参数，比如温度、思维链的开启、上下文token限制，top等。**

### 功能价值

         LLM 节点将大模型能力模块化嵌入流程，通过灵活的提示词配置与数据关联，可实现从简单问答生成到复杂逻辑推理的全场景适配，是工作流实现 AI 智能化的核心枢纽，广泛应用于对话回复、内容创作、信息处理等场景。

## 3.3 知识检索节点与知识库创建

        知识检索节点是 Dify 实现**知识库问答**的核心节点，依托平台内置的知识库能力，从指定知识库中精准检索与用户问题相关的内容，为 LLM 节点提供专业、准确的参考信息，实现基于私有知识的智能问答。而知识库是知识检索节点的数据源基础，需提前完成创建、文档上传与配置，才能支撑检索节点正常工作，以下分别对知识检索节点与知识库创建进行详细说明。

### 知识库创建

![](assets/%E5%A4%A9%E6%9C%BA%E8%B7%A8%E5%A2%83%E6%B2%99%E9%BE%99Dify%E5%9F%B9%E8%AE%AD%E8%B5%84%E6%96%99_VjNubEdWpo.png)

知识库是知识检索节点的数据源底座，需在 Dify 平台完成**新建知识库、上传文档、处理配置、索引构建**等流程，才能为检索节点提供可用的知识数据，具体创建步骤如下：

#### 步骤 1：新建知识库

1. 登录 Dify 平台，进入「知识库」模块，点击「新建知识库」按钮；

1. 配置知识库基础信息：
  - **知识库名称**：自定义名称（如 “企业产品手册库”“行业政策知识库”），便于识别与管理；
  - **知识库描述**：简要说明知识库的用途、覆盖范围（可选）；
  - **权限设置**：配置团队成员的查看 / 编辑权限
  - **索引类型**：默认选择「向量索引」（适配语义检索，是知识库问答的核心索引类型），无需手动修改。

#### 步骤 2：上传知识文档

1. 进入新建的知识库，点击「上传文档」，支持多种文档格式与上传方式：
  - **支持格式**：PDF、Word（docx）、Excel（xlsx）、Markdown（md）、TXT、HTML、PPT（pptx）等主流办公文档；
  - **上传方式**：本地文件上传、在线链接导入、批量上传（支持文件夹批量导入）；

1. 选择需上传的业务文档（如产品手册、政策文件、FAQ 文档等），确认后开始上传。

#### 步骤 3：文档处理与配置

文档上传后，Dify 会自动对文档进行解析、分块、向量化处理，可根据需求调整处理参数：

1. **分块配置**：设置文档分块大小（如 512 字符 / 1024 字符）、分块重叠长度（避免分块割裂知识上下文），适配不同长度的知识内容；

1. **清洗配置**：开启文档清洗功能，自动去除文档中的冗余符号、空白行、格式乱码，提升知识内容质量；

1. **元数据配置**：为文档添加自定义元数据（如文档分类、更新时间、适用部门），便于后续检索筛选与管理。

#### 步骤 4：构建索引(数据向量化)

1. 文档处理完成后，点击「构建索引」，Dify 会基于向量模型将分块后的知识内容转化为向量，完成索引构建；

1. 索引构建完成后，知识库自动生效，可在知识检索节点中直接选择该知识库作为数据源；

1. 后续若更新文档，可重新上传并构建索引，确保知识内容的实时性。

#### 关键配置要点

1. **向量模型选择**：Dify 内置多种向量模型（如文本嵌入向量模型），默认选择适配中文场景的模型，无需手动调整，保障检索精度；

1. **检索模式**：知识库默认支持「语义检索」（基于内容语义匹配，适配自然语言问题），也可开启「关键词检索」，满足精准关键词匹配需求；

1. **知识更新**：支持增量更新，仅对新增 / 修改的文档重新处理，提升索引构建效率，适配高频更新的知识场景。

## 3.4 代码节点与http请求节点

代码节点是 Dify 工作流的**自定义编程扩展节点**，支持 Python 轻量级编程，可突破标准化节点限制，拓展工作流与外部系统交互、复杂逻辑处理的能力边界。

### 核心适用场景

1. **数据库交互**：查询 / 写入数据库数据，如提取用户订单数据、存储 AI 生成内容。

1. **外部服务对接**：调用企业内部 API、第三方开放接口或 Dify MCP 服务，如物流查询、CRM 客户信息调取；

1. **复杂数据加工**：完成格式转换、数据清洗、逻辑计算等，如将非结构化文本转为 JSON、检索结果去重排序；

1. **自定义逻辑判断**：编写多维度条件规则，实现精准的流程分流或异常校验。

### 核心配置项

支持 Python 环境（内置 requests、pymysql 等常用库），可关联工作流变量作为输入，编写代码片段后定义输出变量，支持异常处理兜底配置。

注意点：额外的一些python依赖包内置沙盒环境没有，需要在dify-main\docker\volumes\sandbox\dependencies目录下添加相应requiements。另外dify代码节点里运行时间跟返回的字符都有一定限制，若超过需要在yaml里去扩大相应参数设置。同时要严格定义好相应的输入与输出，让数据能够在工作流里成功流通运转。

## 3.5 迭代与循环节点

       迭代与循环节点是工作流的**批量执行控制节点**，核心解决大批量数据处理、多任务重复执行需求，分为迭代（ForEach）和循环（While）两类。

### 核心适用场景

1. **大批量数据处理**：遍历订单、文档、用户列表等数据集，批量提取、分析或生成内容；

1. **多任务重复执行**：按条件重复调用 API、校验 AI 生成内容，直至满足终止规则；

1. **多分支处理**：实现多任务串行 / 并行执行，提升大批量任务处理效率。

该节点接收数组输入并创建一个子工作流，对每个数组元素运行一次。在每次迭代期间，当前项目及其索引可作为内部节点可以引用的变量。

**核心组件：**

**输入变量** - 来自上游节点的数组数据或列表

**内部工作流** - 对每个元素执行的处理步骤

**输出变量** - 从所有迭代收集的结果（也是一个数组）

                                               

![](assets/%E5%A4%A9%E6%9C%BA%E8%B7%A8%E5%A2%83%E6%B2%99%E9%BE%99Dify%E5%9F%B9%E8%AE%AD%E8%B5%84%E6%96%99_IkgKbxXUbo.png)

配置: 要求数组或列表输入

连接来自上游节点的数组变量，如参数提取器、代码节点、知识检索或HTTP请求响应。

![](assets/%E5%A4%A9%E6%9C%BA%E8%B7%A8%E5%A2%83%E6%B2%99%E9%BE%99Dify%E5%9F%B9%E8%AE%AD%E8%B5%84%E6%96%99_OCZ3bSYsto.jpg)

![](assets/%E5%A4%A9%E6%9C%BA%E8%B7%A8%E5%A2%83%E6%B2%99%E9%BE%99Dify%E5%9F%B9%E8%AE%AD%E8%B5%84%E6%96%99_DGHjbJAGko.png)

注意点：循环节点和迭代节点可以提高对于数据量大时对于模型的一个token输入。防止因为数据量大而导致模型崩溃，同时迭代节点支持多分支任务并发处理，对于同一批数据可同时进行不同任务执行。提高工作流的并发能力。

### 功能价值

避免重复编排相同流程，高效处理批量任务，通过灵活的执行模式和防死循环配置，保障流程稳定性与处理效率。

## 3.6 其它功能节点合集

        这类节点是 Dify 工作流中实现**流程逻辑控制、内容标准化、多源数据整合**的常用基础节点，适配 Chatflow/Workflow 各类场景的精细化编排需求，可与代码、迭代循环、LLM 等核心节点搭配使用，让流程逻辑更灵活、输出更规范、数据处理更高效，以下重点介绍各节点核心定位与适用场景：

### 条件分支节点

**核心定位**：工作流的基础分流控制节点，基于自定义条件判断实现流程多分支跳转。

**适用场景**：按用户输入 / 节点输出的变量结果分流（比如不同的广告策略）；按操作结果做异常分流（如 API 调用成功继续流程、失败触发兜底回复）；按用户属性 / 权限做差异化流程（如会员 / 非会员对应不同问答逻辑）。

**核心定位**：基于自然语言意图识别的智能分流节点，精准判断用户问题意图并匹配对应流程。

**核心定位**：多源分散数据的整合节点，将不同节点的输出变量聚合为结构化数据，方便后续节点统一调用。

# 4. MCP 服务调用

        MCP（Model Context Protocol，模型上下文协议）是 Anthropic 提出的开放协议，核心为大模型搭建与外部 “数据源 / 工具” 的标准化通讯桥梁，类比 Java 界的 Spring Cloud Openfeign（专注微服务通讯），是 Dify 拓展外部资源接入能力的关键方式。

![](assets/%E5%A4%A9%E6%9C%BA%E8%B7%A8%E5%A2%83%E6%B2%99%E9%BE%99Dify%E5%9F%B9%E8%AE%AD%E8%B5%84%E6%96%99_NRlpbPUOCo.jpg)

## 4.1 核心定义与价值

### 核心定位

        解决大模型 “数据孤岛、开发低效、生态碎片化” 痛点，让 Dify 无需定制化开发，即可 “即插即用” 对接本地服务、企业内部系统、第三方工具，实现 AI 与外部资源高效协同。

### 核心价值

1. 打破数据孤岛：直接调用实时数据（外部API）、本地资源（数据库、外部系统），无需手动传输；

1. 降低开发成本：一次实现 MCP 服务端，所有兼容 MCP 的模型均可调用，避免重复开发；

1. 安全与互操作性：内置权限控制和加密机制，标准化协议支持不同厂商工具 “即插即用”；

1. 赋能 Agent 进化：让大模型从 “被动应答” 变为 “主动调用工具”，如自动抓取网页、查询内部系统。

## 4.2 MCP 执行流程

1. 用户向 Dify 应用（Chatflow/Agent）发起提问；

1. LLM 自动匹配已配置的 MCP 服务列表，确定所需工具 / 数据源；

1. 调用目标 MCP 服务器端，传递用户需求指令；

1. MCP 服务器触发对应工具（数据库、API、本地服务）执行操作；

1. 工具执行结果经 MCP 服务器返回给 LLM；

1. LLM 整合结果生成自然语言回复，反馈给用户。

核心结构：

1. 初始化 FastMCP 服务器，定义服务名称、部署地址与端口；

1. 编写辅助函数（可选），封装通用逻辑（如参数转换、基础请求）；

1. 定义 MCP 工具函数（核心），通过装饰器标记，添加函数注解并编写业务逻辑；

1. 启动 MCP 服务，指定传输方式（需与 Dify 配置的 `transport` 一致）。

```
import httpx
from mcp.server.fastmcp import FastMCP

# 1. 初始化FastMCP服务器，定义服务名、部署地址、端口
mcp = FastMCP("Weather Service", host="0.0.0.0", port=8000)

# 2. 编写内部辅助函数（可选）：封装通用逻辑，供工具函数调用
async def _get_lat_long(city_name: str):
    """辅助函数：将城市名称转换为经纬度（调用Open-Meteo地理编码API）"""
    url = "https://geocoding-api.open-meteo.com/v1/search"
    params = {"name": city_name, "count": 1, "language": "zh", "format": "json"}
    async with httpx.AsyncClient() as client:
        response = await client.get(url, params=params)
        data = response.json()
    if not data.get("results"):
        return None
    location = data["results"][0]
    return {
        "name": location["name"],
        "latitude": location["latitude"],
        "longitude": location["longitude"],
        "timezone": location.get("timezone", "UTC")
    }

# 3. 定义MCP工具函数（核心）：@mcp.tool()装饰器标记为可被Dify调用的工具
@mcp.tool()
async def get_weather(city_name: str) -> str:
    """
    获取指定城市的当前天气情况（函数注解：Dify会识别该说明与入参）
    输入：城市名称（如 'Beijing', '上海'）
    输出：包含温度、风速、天气状况的格式化天气报告
    """
    # 调用辅助函数获取经纬度
    location = await _get_lat_long(city_name)
    if not location:
        return f"错误：未找到城市 '{city_name}'，请检查名称是否正确。"

    # 调用天气API获取数据
    url = "https://api.open-meteo.com/v1/forecast"
    params = {
        "latitude": location["latitude"],
        "longitude": location["longitude"],
        "current": ["temperature_2m", "relative_humidity_2m", "apparent_temperature", "weather_code", "wind_speed_10m"],
        "timezone": location["timezone"]
    }
    async with httpx.AsyncClient() as client:
        response = await client.get(url, params=params)
        weather_data = response.json()

    # 解析数据并格式化输出
    current = weather_data.get("current", {})
    units = weather_data.get("current_units", {})
    weather_code = current.get("weather_code")
    # 天气码转换为文字描述
    weather_desc = "未知"
    if weather_code == 0: weather_desc = "晴朗"
    elif weather_code in [1,2,3]: weather_desc = "多云/阴"
    elif weather_code in [45,48]: weather_desc = "有雾"
    elif 51 <= weather_code <= 67: weather_desc = "有雨"
    elif 71 <= weather_code <= 77: weather_desc = "有雪"
    elif weather_code >= 80: weather_desc = "雷雨/阵雨"

    # 格式化返回结果
    return (
        f"--- {location['name']} 天气报告 ---\n"
        f"天气状况: {weather_desc}\n"
        f"当前温度: {current.get('temperature_2m')} {units.get('temperature_2m')}\n"
        f"体感温度: {current.get('apparent_temperature')} {units.get('apparent_temperature')}\n"
        f"相对湿度: {current.get('relative_humidity_2m')} {units.get('relative_humidity_2m')}\n"
        f"风速: {current.get('wind_speed_10m')} {units.get('wind_speed_10m')}"
    )

# 4. 启动MCP服务：传输方式需与Dify配置一致（此处为sse）
if __name__ == "__main__":
    mcp.run(transport="sse")
```

# 5.OpenClaw 与 Skills

## 5.1 什么是 Skills

### 核心定义

       程序性知识的标准化封装。Agent Skills 不仅仅是工具调用（Tools），而是 Agent 解决特定任务的 “程序性知识”。它将自然语言（Prompt / 逻辑）与可执行代码（Scripts）结合，封装了 “如何做” 的完整流程。（可理解为自然语言封装的工作流）

- 本质：它是连接大模型意图与实际业务执行的应用层逻辑。

- 面向人群：不仅限于开发者，领域专家和业务人员也可通过 Markdown 定义业务逻辑。

- 运行机制：通过 “理解意图 -> 触发 Skill -> 运行脚本采集数据 -> 调用模板 -> 生成结果” 的闭环流程完成任务（如自动撰写周报）。

## 5.2 Skills 的完整结构与加载机制

### A. 文件目录结构

一个标准的 Skill 文件夹（如 listing-generator）包含以下核心与可选组件：

#### 🔴 核心必选层 (Core)

- SKILL.md：主指令文件。包含 Prompt 规则、工作流逻辑，是 Skill 的 “大脑”。

- skill.json：元数据文件。定义 Skill 的名称、身份、触发词及分类，相当于 “身份证”。

#### 🟡 扩展可选层 (Extensions)

- templates/：输出模板文件夹（如 Markdown 报告模板），规范最终交付物格式。

- scripts/：可执行脚本文件夹（Python/Shell/JS），用于数据采集或外部调用。

- resources/：参考资料文件夹（如 style-guide.md），提供风格指引或知识库。

- README.md：技能使用说明书。

## 5.5 两者优点与缺点

**以 OpenClaw、Manus 为代表的自主 Agent 平台**

优点: 面向 ToC 普通用户 更加灵活、友好，使用门槛极低，交互自然直观，支持原生 Skills 标准化技能封装，不用复杂编排即可直拿直用，体验轻量化、智能化，Skills 模式也代表了 Agent 能力的未来发展趋势。

缺点: 输出效果稳定性不足，编排化、流程化能力较弱，执行过程存在较大不确定性，更适合短线、轻量、探索类场景；同时 Token 消耗极大，自主执行逻辑不可控，系统运行风险高、企业侧难以管控，目前整体仍属于探索、探讨型产品，暂不适合强稳定要求的生产级业务。

**以 Dify 为代表的工作流式 AI 应用平台**

优点: 更适合追求确定性、稳定输出、强编排的企业级项目与任务，可视化工作流能力极强，完整支持迭代、循环、条件判断、代码节点、外部 API、MCP 协议扩展等全能力组件，流程可控、适合规模化的自动化任务。

缺点：功能搭建流程相对繁琐，配置步骤更多，没有 OpenClaw 那种开箱即用、直拿直用的轻量化体验，对新手的上手成本高于自主 Agent 平台。

# 七、未来场景预期

         基于 Dify 工作流编排能力或openclaw以及calude code的skill能力，我们可以将**电商全业务链路**实现 Agent 化, 覆盖从市场研究、需求分析、产品策划、竞品拆解、数据处理，到运营、广告、文案、客服、供应链的全流程闭环，把零散的人工操作，沉淀为可复用、可触发、可批量运行的标准化 Skill 与可视化工作流。

## 7.1 多专家协同 Agent 场景（多技能联动模式）

        通过**单一总指挥 Agent + 垂直领域专家 Skill** 协同工作，模拟真实电商项目组的多人协作模式，各专家技能各司其职、自动联动，最终输出专业、结构化、可直接落地的业务成果，实现 “一句话启动全流程分析”。

![](assets/%E5%A4%A9%E6%9C%BA%E8%B7%A8%E5%A2%83%E6%B2%99%E9%BE%99Dify%E5%9F%B9%E8%AE%AD%E8%B5%84%E6%96%99_ZJ6EbqfqFo.jpg)

- **需求分析师（Demand Master）**

- 作为消费者行为专家，自动调用 APPFALS、KANO、JTBD 等专业分析模型，深度挖掘用户评论、搜索词与行为数据，完成亚马逊 VOC 需求洞察与痛点提炼，输出标准化需求分析报告。

- **单品拆解专家（Item Master）**

- 自动抓取亚马逊爆款商品详情，还原产品打造逻辑、功能结构、卖点布局与转化路径，完成单品全维度拆解，并输出规范的 HTML 格式拆解文档。

- **竞品可视化拆解专家（Visual Masters）**

- 专注竞品视觉与营销策略分析，自动识别主图、视频、A + 页面、排版逻辑与营销话术，提取显性化策略、弱点遮蔽手法、高转化钩子，为自身产品优化提供依据。

- **产品策划总监（Products Master）**

- 作为总协调与汇总出口，整合需求分析、单品拆解、竞品分析的全部结论，统筹输出完整的《亚马逊新品定义与视觉企划案》，形成可直接执行的产品开发与上架方案。

- **数据结构化专家（Data Master）**

- 自动完成亚马逊商品数据清洗、表结构识别、数据规整，区分主表与评论表，统计有效商品量、总评论数、有效评价占比等核心指标，为后续分析提供干净、可用的数据集。

- **市场分析师（Marketing Master）**

以麦肯锡式战略分析能力结合一线实战经验，自动分析类目容量、竞争格局、垄断程度、供需关系，生成可视化 HTML 仪表盘与市场战略判断，支撑选品与投入决策。
