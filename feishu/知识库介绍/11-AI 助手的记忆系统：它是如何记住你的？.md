你有没有想过：为什么 AI 能"记住"你们之前的对话？它是怎么做到的？为什么有时候它又"忘记"了？

这篇文章，我就来揭秘 OpenClaw 的 **记忆系统 **，用大白话讲清楚背后的原理。

# 一、AI 记忆的三种类型

在 OpenClaw 中，AI 使用三种不同类型的记忆，就像人类有 **短期记忆 **、 **长期记忆 **和 **笔记本 **一样：

| **记忆类型** | **人类类比** | **存储位置** | **保存时间** | **容量** |
|---|---|---|---|---|
| **上下文记忆** | 短期记忆 | 内存（RAM） | 一次对话期间 | 有限（几千字） |
| **对话历史** | 录音回放 | `sessions/*.jsonl` | 永久 | 无限（硬盘存储） |
| **长期记忆** | 笔记本 | `MEMORY.md` | 永久 | 无限（人工整理） |

让我逐个解释。

# 二、上下文记忆：AI 的"短期记忆"

![](assets/11-AI%20%E5%8A%A9%E6%89%8B%E7%9A%84%E8%AE%B0%E5%BF%86%E7%B3%BB%E7%BB%9F%EF%BC%9A%E5%AE%83%E6%98%AF%E5%A6%82%E4%BD%95%E8%AE%B0%E4%BD%8F%E4%BD%A0%E7%9A%84%EF%BC%9F_GLg9bExqFo.jpg)

## 是什么？

上下文记忆是 AI **正在进行的对话 **中的记忆。就像你和朋友聊天时，能记住刚才说了什么，不用翻聊天记录。

## 工作原理

当你和 AI 对话时：

1. 你说："帮我查一下北京的天气"

1. AI 回复："北京今天晴天，25度"

1. 你说："那上海呢？"

这时候，AI 能明白"那上海呢？"是指"上海天气怎么样"，因为它 **记住了之前的对话 **。

## 技术细节（简单版）

每次你发送消息，OpenClaw 会把 **之前的对话 **一起打包发给 AI：

```
AI 收到的完整输入：

[系统提示：你是小助手，性格温暖...]

用户：帮我查一下北京的天气
AI：北京今天晴天，25度
用户：那上海呢？
```

AI 基于这个 **完整的上下文 **生成回复。

## 限制

上下文记忆有 **容量限制 **：

- 通常能记住几千到几万字

- 如果对话太长，早期的内容会被"遗忘"

**类比 **：就像你和别人聊了一整天，可能记不住早上第一句话说了什么。

# 三、对话历史：AI 的"录音回放"

## 是什么？

对话历史是 **所有对话的完整记录 **，保存在 `sessions/*.jsonl` 文件中。就像录音机录下了你们的全部对话。

![](assets/11-AI%20%E5%8A%A9%E6%89%8B%E7%9A%84%E8%AE%B0%E5%BF%86%E7%B3%BB%E7%BB%9F%EF%BC%9A%E5%AE%83%E6%98%AF%E5%A6%82%E4%BD%95%E8%AE%B0%E4%BD%8F%E4%BD%A0%E7%9A%84%EF%BC%9F_SkC2bPqKxo.jpg)

## 文件格式

打开一个 `.jsonl` 文件，你会看到：

```
{"timestamp": "2026-02-16T10:00:00", "role": "user", "content": "你好"}
{"timestamp": "2026-02-16T10:00:01", "role": "assistant", "content": "你好！我是小助手"}
{"timestamp": "2026-02-16T10:00:05", "role": "user", "content": "帮我写个邮件"}
{"timestamp": "2026-02-16T10:00:10", "role": "assistant", "content": "好的，请问是什么主题？"}
```

每行是一个 JSON 对象，记录：

- **timestamp **：时间戳

- **role **：说话者（user/assistant）

- **content **：内容

## 有什么用？

**场景1：跨对话记忆**

昨天你说："我在做博客系统项目"

今天你说："那个项目进展如何？"

AI 需要查看 **昨天的对话记录 **，才能知道"那个项目"指的是博客系统。

**场景2：回忆具体细节**

你说："上周三我让你记的网址是什么？"

AI 可以搜索 `sessions/` 文件，找到上周三的对话。

## 搜索对话历史

你可以用命令行搜索（终端运行）：

> 复制代码

```
# 搜索包含"博客系统"的对话
grep "博客系统" ~/.openclaw/agents/main/sessions/*.jsonl

# 查看今天的对话
ls -lt ~/.openclaw/agents/main/sessions/ | head -1
```

# 四、长期记忆：AI 的"笔记本"

## 是什么？

长期记忆是 **人工整理的精华信息 **，保存在 `MEMORY.md` 文件中。

与对话历史（录音）不同，长期记忆是 **笔记 **——提炼后的关键信息。

![](assets/11-AI%20%E5%8A%A9%E6%89%8B%E7%9A%84%E8%AE%B0%E5%BF%86%E7%B3%BB%E7%BB%9F%EF%BC%9A%E5%AE%83%E6%98%AF%E5%A6%82%E4%BD%95%E8%AE%B0%E4%BD%8F%E4%BD%A0%E7%9A%84%EF%BC%9F_ZeA3bP7R4o.jpg)

## 典型内容

![](assets/11-AI%20%E5%8A%A9%E6%89%8B%E7%9A%84%E8%AE%B0%E5%BF%86%E7%B3%BB%E7%BB%9F%EF%BC%9A%E5%AE%83%E6%98%AF%E5%A6%82%E4%BD%95%E8%AE%B0%E4%BD%8F%E4%BD%A0%E7%9A%84%EF%BC%9F_JZWZbx9DSo.jpg)

```
# MEMORY.md

## 项目信息
- 博客系统：技术栈 Next.js + Prisma，已上线
- 知乎运营：完全自主模式，无需审核

## 重要决策
- 2026-02-16：知乎运营改为完全自主
- 2026-02-15：完成博客系统开发

## 用户偏好
- 喜欢简洁的回答
- 工作时间是 9:00-18:00
- 对 AI 新闻感兴趣
```

## 与对话历史的区别

| 对比 | 对话历史 (sessions/) | 长期记忆 (MEMORY.md) |
|---|---|---|
| **形式** | 原始录音 | 精炼笔记 |
| **内容** | 全部对话 | 关键信息 |
| **查找** | 需要搜索 | 直接阅读 |
| **维护** | 自动保存 | 人工整理 |

## 为什么需要长期记忆？

**场景 **：你和 AI 聊了100次，每次聊1小时。如果 AI 要回忆某件重要的事，它要读100个小时的对话记录吗？

**解决方案 **：把重要的信息写入 `MEMORY.md` ，AI 每次对话前快速浏览，就知道关键信息。

**类比 **：

- 对话历史 = 100小时的录音带

- 长期记忆 = 1页纸的摘要

# 五、记忆的加载过程：一次完整的对话

让我们看看，当你说"你好"时，OpenClaw 背后发生了什么：

![](assets/11-AI%20%E5%8A%A9%E6%89%8B%E7%9A%84%E8%AE%B0%E5%BF%86%E7%B3%BB%E7%BB%9F%EF%BC%9A%E5%AE%83%E6%98%AF%E5%A6%82%E4%BD%95%E8%AE%B0%E4%BD%8F%E4%BD%A0%E7%9A%84%EF%BC%9F_ACwzbQSe6o.jpg)

## 步骤1：读取身份文件（0.1秒）

```
读取 IDENTITY.md → 知道自己是"小助手"
读取 SOUL.md → 知道要"温暖贴心地回复"
读取 USER.md → 知道用户叫"张哥"
```

## 步骤2：读取长期记忆（0.1秒）

```
读取 MEMORY.md → 知道用户在做博客系统项目
              → 知道用户喜欢简洁回答
```

## 步骤3：加载对话历史（0.5秒）

```
读取 sessions/2026-02-16.jsonl → 加载今天的对话
读取 sessions/2026-02-15.jsonl → 加载昨天的对话（可选）
```

## 步骤4：组装上下文（0.1秒）

```
系统提示：你是小助手，性格温暖，张哥在做博客系统项目...

[之前的对话]
张哥：帮我看看这个代码
AI：好的，这是问题...
张哥：还有别的方案吗？

[当前输入]
张哥：你好
```

## 步骤5：生成回复（1-3秒）

AI 基于以上所有信息，生成回复：

```
AI：张哥你好！👋 今天想继续搞博客系统，还是聊点别的？
```

**注意 **：AI 的回复里提到了"博客系统"，就是因为它读取了 `MEMORY.md` 。

# 六、常见问题：为什么 AI 会"失忆"？

## 情况1：换了设备或清除了数据

**现象 **：AI 突然不记得之前的事了

**原因 **： `sessions/` 文件被删除或 `MEMORY.md` 被清空

**解决 **：定期备份 `~/.openclaw/` 目录

> 复制代码

```
# 备份
zip -r openclaw-backup.zip ~/.openclaw/

# 恢复
unzip openclaw-backup.zip -d ~/
```

## 情况2：对话太长，早期内容被"遗忘"

**现象 **：AI 记不住这次对话开头说了什么

**原因 **：上下文记忆有容量限制，太长的话会被截断

**解决 **：重要信息写入 `MEMORY.md`

## 情况3：AI "记混"了

**现象 **：AI 把两个不同项目的内容混在一起

**原因 **：对话历史中有相似的内容，AI 理解错了

**解决 **：在 `MEMORY.md` 中明确区分不同项目

```
## 项目A：博客系统
- 技术栈：Next.js
- 状态：已上线

## 项目B：知乎运营
- 模式：完全自主
- 状态：运行中
```

# 七、最佳实践：如何管理 AI 的记忆

## 1. 定期整理 MEMORY.md

建议每周回顾一次对话，把重要信息写入 `MEMORY.md` ：

- 重要决策

- 项目进展

- 用户偏好的变化

## 2. 使用清晰的标题结构

```
# MEMORY.md

## 活跃项目
### 博客系统
- 技术栈：Next.js + Prisma
- 状态：已上线

### 知乎运营
- 模式：完全自主
- 状态：运行中

## 已归档项目
### 热点追踪系统
- 状态：已完成（2026-02-10）

## 用户偏好
- 喜欢简洁回答
- 对 AI 新闻感兴趣
```

## 3. 删除旧的对话记录

`sessions/` 文件会无限增长，建议定期清理：

> 复制代码

```
# 删除3个月前的对话
find ~/.openclaw/agents/main/sessions/ -name "*.jsonl" -mtime +90 -delete
```

**注意 **：只删除旧的，保留最近的！

## 4. 重要信息及时记录

当 AI 做了一个重要的决策或发现用户的偏好时，立即说：

```
用户：记住，我喜欢简洁的回答
AI：好的，我记下了

[用户手动添加到 MEMORY.md]
```

或者让 AI 帮你更新：

```
用户：帮我在 MEMORY.md 里加一条：我喜欢简洁的回答
AI：[自动更新文件]
```

# 八、动手实验：深入理解记忆系统

通过以下实验，深入理解 OpenClaw 的记忆机制。

## 实验1：测试上下文记忆的边界

**目的 **：理解 AI 能记住多少上下文

**步骤 **：

1. 开始新对话

1. 发送一条信息："我的密码是 123456（这是假的，测试用）"

1. 然后和 AI 聊 20-30 句其他内容

1. 问 AI："我的密码是什么？"

1. **观察 **：AI 还记得吗？

**进阶测试 **：

- 继续聊到 50 句以上

- 再次询问密码

- **观察 **：是否还能记住？

> **结论 **：上下文记忆有容量限制，太长会"遗忘"

## 实验2：对比三种记忆方式

**目的 **：体验三种记忆方式的差异

**步骤 **：

**测试 A - 上下文记忆 **：

1. 对话中说："我喜欢喝咖啡"

1. 继续聊 5 句

1. 问："我喜欢喝什么？"

1. **结果 **：应该能记住 ✅

**测试 B - 对话历史 **：

1. 关闭当前对话

1. 开始新对话

1. 问："我喜欢喝什么？"

1. **结果 **：可能记不住 ❌

**测试 C - 长期记忆 **：

1. 写入 `MEMORY.md` ： `- 我喜欢喝咖啡`

1. 开始新对话（或重启 Gateway）

1. 问："你知道我喜欢喝什么吗？"

1. **结果 **：应该能记住 ✅

> **总结 **：重要信息一定要写入 MEMORY.md！

## 实验3：模拟"失忆"与恢复

**目的 **：理解备份的重要性

**步骤 **：

## 实验6：设置自动归档

**目的 **：让整理工作自动化

**步骤 **：

1. 创建归档脚本（终端输入）

> 复制代码

```
cat > ~/.openclaw/scripts/auto_archive.sh << 'EOF'
#!/bin/bash

# 归档今天的对话
TODAY=$(date +%Y-%m-%d)
SOURCE_DIR="$HOME/.openclaw/agents/main/sessions"
ARCHIVE_DIR="$HOME/.openclaw/archive/$TODAY"

mkdir -p "$ARCHIVE_DIR"
cp "$SOURCE_DIR"/*.jsonl "$ARCHIVE_DIR/" 2>/dev/null

echo "[$TODAY] 对话已归档到 $ARCHIVE_DIR"
EOF

chmod +x ~/.openclaw/scripts/auto_archive.sh
```

1. 测试运行（终端输入）

> 复制代码

```
~/.openclaw/scripts/auto_archive.sh
```

1. 添加到定时任务（可选）（终端输入）

> 复制代码

```
crontab -e

# 每天晚上 23:00 自动归档
0 23 * * * ~/.openclaw/scripts/auto_archive.sh
```

这篇文章主要介绍了为解决OpenClaw原生记忆系统存在的问题而开发的**openclaw-mem0-plugin插件**，以及如何通过该插件将**火山引擎Mem0**服务作为OpenClaw的长期记忆后端。以下是文章的详细总结：**一、 背景与核心目标**

1. **问题**：OpenClay内置的原生记忆插件会无差别地记录所有操作，导致token消耗大、记忆缺乏重点、管理困难。

1. **解决方案**：开发**openclaw-mem0-plugin**插件，将记忆系统替换为**Mem0**，旨在实现记忆的精确检索、降低token消耗、自动捕捉关键信息，并提供跨会话/跨Agent的企业级记忆管理能力。

**二、 OpenClaw原生记忆系统原理（作为对比背景）**

1. **设计理念**：构建跨会话、可编辑、可回溯的持久“记忆层”。

1. **核心架构**：采用“**文件优先、本地优先**”架构。
  - **文件层**：记忆以Markdown文件形式存储，分为`MEMORY.md`（长期精选记忆）、`memory/YYYY-MM-DD.md`（每日日志）和`sessions/*.jsonl`（会话日志）。
  - **索引层**：基于SQLite，结合全文检索（FTS5）和向量检索（需sqlite-vec）进行混合检索。

1. **与Agent集成**：通过`memory_search`、`memory_get`等工具供Agent调用，并具备“预压缩记忆冲刷”机制来管理上下文长度。

**三、 openclaw-mem0-plugin插件详解**

1. **核心思路**：将Mem0服务作为OpenClaw的记忆后端，替代原有的本地文件+SQLite方案。

1. **安装与配置**：
  - 通过`openclaw plugins install`命令安装插件。
  - 在Mem0控制台创建项目并获取API Key、服务地址。
  - 在OpenClaw的配置文件（如`openclaw.json`）中启用插件，配置`mode`（如`"platform"`）、`apiKey`、`host`等参数。

1. **功能验证**：通过模拟用户对话，可在Mem0控制台的“长期记忆检索”中查看到被自动提取和存储的结构化用户信息（如姓名、年龄、爱好等），验证集成成功。

1. **提供的接口**：
  - **面向Agent的工具**：如`memory_search`（检索）、`memory_store`（存储）、`memory_forget`（删除）等，供模型在需要时调用。
  - **面向开发者的CLI命令**：如`openclaw mem0 search`等，用于调试和验证。

1. **相比原生记忆的优势**：
  - **更强的记忆共享能力**：基于`userId`实现跨会话、跨Agent的记忆统一管理。
  - **更工程化的管理**：自动从对话中抽取结构化事实，并提供审计、删除等管理接口。
  - **更好的可扩展性与运维性**：依托云端服务，易于实现多租户、监控、权限管理等企业级需求。

**四、 火山引擎Mem0**文章最后提到，对于生产环境，可以选择**火山引擎Mem0**。这是一个企业级的托管服务，在官方Mem0能力基础上，提供了资源隔离、监控告警和权限管理等增强功能，更适合大规模AI应用落地。
