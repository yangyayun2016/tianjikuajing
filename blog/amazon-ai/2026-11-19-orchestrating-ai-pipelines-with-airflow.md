前几天把 DataCamp 上的一篇教程读完了：Andrea Valenzuela 写的《用 Airflow 编排 AI 流水线》，页面标注的发布/更新日期是 2026-10-06。这篇不太像常规的 Airflow 入门文，它真正回答的是我们做 AI 工作流时最常卡住的那一步——demo 跑通之后，怎么让它每天稳定地跑。

先说明：下面是我们的学习笔记，不是教程的翻译或再版。想看完整代码、安装步骤和原始示例，请直接去读原文。这里只写我们读到的结构、认同的判断，以及对自己流程的启发。

## 一、从「一个笔记本 + 一个 API」到「每天稳定跑」，差在哪里

教程开头的判断很直接：做一个 AI 原型很容易，一个 notebook、一个 API key、几十行 Python，就能完成文本分类、摘要或推荐。但让它在生产里每天跑，是完全另一件事。

问题通常集中在几个地方：

- 模型 API 有速率限制，一批数据跑下来总会撞上；
- 单个请求会超时；
- 返回的 JSON 语法合法，但字段缺了，或者标签不在预期集合里；
- 下游的数据库、对象存储暂时不可用；
- 某一步失败了，你想只重跑那一步，结果把已经成功的部分又跑了一遍，产生重复数据。

这些问题和「模型好不好」没有关系。教程的说法是：当一条 AI 流水线变成周期性工作流，可靠性、监控与恢复的重要性会迅速追上模型本身。这句话我们完全同意。

## 二、教程在讲什么

它用一个小例子把整条链路走通：每天把客户评价拉进来，用 LLM 给每条评价打情感标签（正面 / 中性 / 负面），最后把结果存成结构化文件。真实业务里数据可能来自 API、数据库或对象存储；教程用本地 JSONL 文件代替，只是为了让例子能跑起来。

真正值得看的是它怎么组织这三步。

**把每一步定义成独立任务，并显式声明依赖。** 整条流水线是一个 DAG（有向无环图），不是一段从头写到尾的脚本。每一步有自己的状态、日志和重试策略，失败的时候你知道是哪一步、哪条数据出的问题。

**用结构化输出约束模型。** 教程让模型按固定字段返回（评价 ID 加三个标签之一），而不是自由文本。这看起来只是工程细节，实际上是后面所有校验与存储的前提——下游拿到的东西必须是可预期的。

**按条拆任务，而不是一次丢给模型。** 教程用了动态任务映射：一条评价对应一个任务实例。五十条评价里有一条失败，只需要重试那一条，其余四十九条不用重跑；也不会因为一次塞太多文本而撞上上下文限制。

**重试是有策略的，不是死循环。** 失败后先等一小段时间再试，等待时间逐次拉长，并设上限。临时性的限流和网络抖动通常这样就能过去；如果是提示词或者数据本身的问题，重试几次仍然失败，那就该让人看见。

**日志不等于存储。** 中间那个把分类结果打印出来的任务，是为了开发时检查；最后一步才是写入结构化文件。日志适合看，不适合当数据源。

教程还提到两个更进一步的模式：一是由外部事件触发，而不是每天固定时间跑；二是流程中间可以暂停、等人批准或修改。这两点后面再说。

## 三、对我们自己的 AI 流程，有几点是真能用上

**第一，把失败当成常态来设计，而不是当异常来处理。**

我们做评论文档处理这类任务时，最容易犯的错就是假设「接口会成功」。某天批量任务中途断了，就得人工去找断点。把「失败 → 重试 → 仍然失败 → 告警或人工介入」这条路径提前画进流程，比事后补脚本便宜得多。

**第二，不要用 cron 硬撑多步依赖。**

一个定时任务跑一个脚本，很够用。但当流程变成「抓取 → 清洗 → 模型处理 → 校验 → 入库 → 通知」，cron 只能告诉你几点开始跑。它不知道第三步失败了第四步该不该跑，也不会帮你只重跑失败的那一段。这时候需要的不是更强的脚本，而是一层编排。

**第三，校验要放在模型和存储之间。**

模型输出「看起来对」和「能入库」是两件事。中间加一步校验：字段齐不齐、标签在不在允许集合里、条数对不对得上输入。校验不过就让流程停下来，比脏数据进了库再回头捞要省事得多。

**第四，人工确认应该是一个正式的步骤。**

教程提到流程可以中途暂停、等审核者批准、拒绝或要求修改。这一点对我们特别有共鸣。选品研究、竞品报告、对外内容这类工作，不可能全自动放行。把「人看一眼」设计成流程里的一个节点，而不是散落在聊天窗口里的口头确认，责任和记录都会清楚很多。

**第五，凭据不要写在代码里。**

教程把 API key 放在连接配置里，DAG 代码中不出现密钥。这既是安全要求，也让同一份流程能在不同环境跑。我们的内部规范也是这样：密钥只存在于运行环境，不进仓库，也不进任何文稿。

**第六，小处也别偷懒。**

教程在常见问题里自己承认，示例是直接写最终文件的，生产环境应该先写临时文件再原子替换，避免下游读到写了一半的结果。这种细节没人会兴奋，但它决定了半夜出问题时你要不要起床。

## 四、结尾

这篇教程值得读的地方，不是它教你装了什么包，而是它把「AI 流水线」拆成了几个可以被检查的部分：任务边界、依赖、重试、校验、存储、人工确认。模型只是其中一环。

原文在这里，建议自己读一遍：
https://www.datacamp.com/zh/tutorial/orchestrating-ai-pipelines-with-airflow

我们会继续把这套编排思路用在自己的 AI 流程里：先把步骤和依赖写清楚，再谈自动化和提速。如果你的 AI 工作流还停在一个 notebook 加一个定时任务，这篇是个不错的起点。
