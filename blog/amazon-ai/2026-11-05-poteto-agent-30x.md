最近我们在持续跟 Lauren Tan（X [@poteto](https://x.com/poteto)）——她现在在 SpaceXSI / Grok Bot，背景横跨 React Compiler、Cursor、Meta、Netflix。她的内容有个稳定特征：**很少讲「模型多强」，几乎都在讲「人怎么改环境，让 agent 少犯错」**。这对我们做跨境业务系统、带一堆岗位 Bot 的团队，比追热点更有用。

下面按「可迁移实践 → 架构优先级 → 我们怎么落地」写一版学习笔记（事实与链接以 2026-11-05 的公开更新整理为准）。

## 1. 约 30x 发码，前提是 agent-friendly 架构

她提到团队拿到大约 **30x 的发码量**，人不再逐行读代码，性能没有掉；同时要「驯服 slop」；10 月大约有 **230 人**给 Grok Bot 合过 PR。相关帖：[30x / AIE](https://x.com/poteto/status/2118017093677494706)。

这组数字容易被误读成「上 agent 就能 30x」。真正的因果是反的：

- 先把**环境、类型、检查、目录结构**改到 agent 能自己跑通，速度才出现；
- 人从「逐行审代码」退到「审接口、审边界、审结果」；
- 没有确定性检查兜底，30x 只会变成 30x 的技术债。

对应到跨境运营 / SI Bot：**先修跑道，再放飞机。** 广告健康规则、打标本体、字段字典要先写进 skill / 仓库，再谈扩 bot 数量。

## 2. `/statechart`：先画状态机，再让 agent 动手

新加的 `/statechart`（配合 TLA+）很朴素：**站在用户视角画出状态图，用它核对 agent 到底有没有理解目标**。[原帖](https://x.com/poteto/status/2118073519515025804)

agent 最常见的失败不是「不会写」，而是「目标理解偏了还写得很顺」。状态图是低成本的照妖镜：有哪些状态、谁能迁移、哪些不可逆；哪些事件必须先有数据、哪些必须先有人批；出错时退到哪。

所以做广告健康巡检、关键词打标流水线之前，应该先画状态机，而不是先写 prompt。

## 3. 别让自己当瓶颈

多任务并行时，**不要先去开新 UI**，先看看自己是不是卡住了整条链路。[原帖](https://x.com/poteto/status/2117899425733554628)

团队里最贵的瓶颈往往不是模型，而是「只有某个人能批、只有某个人知道口径、只有某个人能发版」。可操作的做法：

- 审批门只拦**高风险**动作，低风险的先放行；
- 把「我知道但没写下来」的东西固化成 skill / 规则 / 字段定义；
- 能自动回读验证的，不要排人工 review 队列。

## 4. `/automate-me`：fork 自己的 Bot 工厂

她的做法是把自己的工作方式做成可 fork 的模式（`poteto-mode`），再用插件扩展出专岗 bot。[原帖](https://x.com/poteto/status/2118055219431109042)

判断很清楚：**bot 不该是一个万能助手，而应该是一条能复制岗位的生产线。** 一个岗位跑通 → 打包成 skill/插件 → fork 出下一个岗位。这和我们「一岗一责」的 RoleSpec 思路是对齐的。

## 5. 合并前 agent 自检，不再只靠传统 CI

最新做法是：**在合并前让 agent 自己完成一轮自检**，而不是把全部信任压在传统 CI 上。[原帖](https://x.com/poteto/status/2117453342477852824)

分工变化：

- 传统 CI 管**确定性**：类型、lint、单测、构建；
- agent 自检管**语义**：改动是否真的解决了问题、有没有越权、有没有偷偷改口径、边界有没有覆盖；
- 人只看自检结论 + 高风险点。

多轮 agent review 会把 PR 「overcook」（越改越肿），所以她更偏好**少一点对抗式抽象 review，多一点实测和确定性检查**。

## 6. 日常口令与闭环

pstack 里最值得抄的两个口令：

- **`/correct`**：每次纠正 agent，把纠正沉淀成规则，而不是聊完就完；
- **`/in-your-own-words`**：让 agent 用自己的话复述任务，暴露理解偏差——和 `/statechart` 是同一套思路的两种粒度。

再加上 First mile（日历、CRM、Slack、邮件等真实入口）/ Last mile（复杂改仓交给云端写码）/ 闭环 Loop（盯频道 → 工单 → 复现 → 小群验证 → 通知 / 合并）。闭环的关键不是自动化率，而是**每一环都有回读**。

插件入口：[pstack（Grok）](https://x.ai/bot/plugin/9717366) · [Cursor Marketplace](https://cursor.com/marketplace/cursor/pstack) · [源码](https://github.com/cursor/plugins/tree/main/pstack)

## 架构纠正优先级（建议贴墙）

```
更好的架构 / 数据结构  >  lint、测试进 CI  >  skill / rule  >  纯靠人审
```

1. 同一个错误反复出现，先怀疑**数据结构或架构**错了，别急着加规则；
2. 架构一时改不动，就把检查**前移到 CI**；
3. 再不行，写成 **skill / rule**；
4. **纯靠人审是最后一道，也是最贵、最不可靠的一道。**

我们常见的反模式正好倒过来：出了事故 → 加一条「请人工确认」→ 人越来越忙 → 真正的架构问题一直没动。

## 对天机跨境 SI Bot 的落地建议

我们已有一岗一责的 RoleSpec、权限分级、红线与高风险须人批。不需要「再上一个 agent 平台」，而是把这套方法**灌进现有骨架**。

**第一周（低成本三件事）**

1. 给广告健康巡检、关键词打标各画一张用户视角状态机，贴进对应岗位说明，作为验收依据。
2. 把字段字典、ABA 口径、健康阈值、打标规则写进 skill 与规则目录；人工纠错走一遍「纠正 → 沉淀规则」。
3. 审一遍审批门：只拦对外发送、动资金、承诺交付、删除数据这类不可逆动作；低风险查询与分析默认放行。

**第二到四周**

4. 双层验收：确定性层（schema、规则引擎回读、报表比对）+ 语义层（是否越权、是否编造、是否改口径、结论是否有来源）。
5. 一个改动超过两轮 agent 互审就停，改成用真实数据回读验证，避免 overcook。
6. 广告类结论以报表回读与规则引擎为准，不以「觉得对」为准。

**月度**

7. 选一个已跑顺的岗位，打包成「岗位说明 + skill + 固定交付模板」，再 fork 相邻岗位。
8. 先接真实输入流（飞书/Slack、周报、工单），复杂改仓再交给云端编码 agent。
9. 从 3 个 bot 扩到 10 个之前，先问：契约齐不齐？检查进没进 CI？口径是不是还只在某个人脑子里？

**红线**：agent 提速的前提是**可追溯 + 可回读 + 高风险必须人批**。30x 的前提是架构友好，不是胆子大。

## 一句话

@poteto 这一轮真正在讲的，不是「agent 多能干」，而是：**把架构、类型、状态机、规则这些环境修好，人退出逐行审查，只保留高风险决策权**——然后速度会自己出现。
