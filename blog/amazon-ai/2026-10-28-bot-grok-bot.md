核心思路是把“人”放在最上面，只做决策。

* **人（我）**：只拍板，不搬砖。
* **幕僚长 Bot**：总协调。各个专员的产出它来汇总，遇到要花钱、要改方向的事，它往上升级给我。
* **专员 Bot**，按职能分组：
* 选品与产品：选品情报、产品经理、采购专员
* 运营与广告：亚马逊运营、亚马逊广告助手、ASIN 风控专员、自动化运营
* 内容：视觉内容、公众号、PPT 专家、bailingads 网站建设
* 后台与支持：云服务器架构、知识库、财务主管、日常助理（Mac 管家）、英语专家

晚上回家休息，电脑一关；或者在外面出差、旅游，我经常就拿着手机，远程指挥这支 Grok Bot 团队把事情干完。

打开就是这个界面：最上面是 Grok Bot 和幕僚长，下面一排是各个专员，日常助理、云服务器架构、公众号、广告助手、选品情报、PPT 专家、视觉内容……谁回了消息、谁还在干活，一眼就看到。

说实话，这套还没到「完全成熟」的程度，但这个工作方式真的很好，值得分享。

这里顺便说一个我自己的体会：

* **Codex 这类项目型工具**，是围绕「项目」组织的。项目做完，这一摊也就结束了。
* **Grok Bot** 是围绕「人/角色」组织的。项目会结束，但团队成员还在，而且会跟着你一起，越用越顺手、一起成长。

1. **数据怎么接：MCP 连接器**

Bot 再聪明，没数据也是瞎猜。我接了这几样：

* **领星 ERP**：授权了多个店铺。读广告、读订单随便读；**所有写操作都要我人工确认**。
* **Helium 10 官方 MCP**：通过 OAuth 授权接到 mcp.helium10.com，账号密码不经过 Bot。常用的是 ABA、SQP、Cerebro 反查、关键词搜索量这些数据，另外我还挂了一个中转做补充。
* **MyLevis 通用 MCP**：这个值得单独说一句。很多卖家手上同时开着好几个数据工具，每个都要单独配。MyLevis 的思路是把一堆跨境工具汇总到一个 MCP 入口里。按官网 MYLEVIS HUB 页面的介绍，目录里有卖家精灵、Helium 10、Sorftime（国内做亚马逊选品和市场数据的软件）、Keepa、SIF、Kalodata、极目数据（Jiimore）等，官方称连接 389+ 个跨境电商 MCP、覆盖 22 家工具平台。按积分计费，不同工具单价不一样，新用户注册送试用积分。我的感受是省了很多配置的功夫；具体每个工具能调到多深，还是以各家的接入说明为准。
* **阿里云服务器**：放 skills 和知识库，跑领星的开放 API。安全上做了加固：SSH 只允许密钥登录，每天自动备份。
* **本地紫鸟**：店铺登录只留在本地紫鸟，**绝不上云**。这条是红线。

另外，Listing 图片是在 Mac 上用 Codex 做的。各类日常任务都按 routine 定时跑，我不在线它也照跑。

2. **它实际在干什么**

说几个已经跑通的节点：

**10/17：开放 API 自动上架**

第一个品通过领星开放 API 自动上架成功。新品审核最长要等 48 小时，这段时间 Bot 自己盯着。

**10/18：第一单 FBM 全链路跑通**

订单进来 → 推给供应商/海外仓代发 → 单号通过领星 submitFulfillment 回传，自动标记 Complete。

10/20 打印亚马逊FBA标签，

10,22 广告优化

**卖家后台全程没手动传单号。** 唯一要人的地方是付款，这一步等我点。

**每日选品**

每天推 5-7 个品，带利润测算，再做四个维度的体检：流量、竞争度、ABA 头部三家是否垄断等。过不了的直接淘汰，不浪费我时间。

**图片规则**

图上的 logo 必须和 Listing 品牌一致；A+ 文案避开禁用词。这些写进了视觉 Bot 的规则里，不靠我每次提醒。

**还有这些在跑：**

* ASIN 风控监控
* 广告调整建议
* 公众号写作（对，这篇的初稿就是它出的，我改）

3. **人守的几道闸**

全自动不等于放手不管。下面这些**必须我批**：

* 压货
* 加钱
* 改品
* 喊停
* 付款
* 以及**所有写操作**

逻辑很简单：可逆的、读数据的事让 Bot 干；不可逆的、花钱的事人来按按钮。

5. **对比 10/12 上线**

10/12 刚上线时，bailingads.com 只有一个功能：**SIS 搜索词份额诊断**。

现在首页已经能看到这些：

* **SIS 份额诊断**：看清每个词市场有多大、你拿了多少份额，自动列出该否、该加投、该调价的词。
* **SP 搜索词诊断**：按盈亏平衡 ACoS / 目标 ACoS 来判断词的去留。
* **Bulk 账户体检**：上传「批量操作」下载的 Bulk 文件，整体看账户问题。

用法三步：后台导出报表 → 拖进网页 → 勾选建议、下载调整表回后台上传。目前支持 SP，SB、SD、DSP 在共建计划里。

6. **Grok Bot 对卖家的价值**

* **一支专员团队**：选品、运营、广告、内容、财务各有专人（专 Bot）。
* **你下线它还在干**：routine 定时跑，早上起来看结果就行。
* **能接你的 ERP 和数据工具**：领星、Helium 10 这类通过 MCP 接进来，基于真实数据干活。
* **人守不可逆的闸**：花钱、写操作、改方向，永远是你拍板。

一句话：BailingADS 帮你把广告报表变成动作，Grok Bot 帮你把整个运营变成一支不下班的团队。

7. **高手们怎么用，以及我接下来要改的**

前面说的都是我自己的做法。这两天我专门去翻了翻，国外的卖家、做 AI 的团队，是怎么用这类“AI 团队”的。挑几个有公开出处的说说。

8. **Grok Bot 官方的建团队思路：先一个，再慢慢加。**

官方文档建议先让一个 Bot 对一个完整结果负责，等某项工作稳定成固定专岗了，再加新的 Bot；花钱、发送、删除、改线上这些动作，一律放在审批后面。

卖家能借的：别一上来就建十几个 Bot。先让一个“运营总管”跑顺，再拆广告、财务。

9. **bfrench：很多 Bot 其实应该是技能（skill）。**

他在 X 上写过一篇《Bots that Should be Skills》，意思是一个流程跑通了，第一反应是给它起名、单独开个 Bot，但很多时候没必要，还会加重那台共用电脑的负担。

卖家能借的：每天拉报表、每周对账这种固定动作，做成技能 + 定时任务就够了，不一定要单独一个 Bot。

10. **Michael Fenech：给你的 Bot 团队做备份。**

他发帖提醒：越依赖 Grok Bot，从零重建就越难。他给了一套提示词，让 Bot 定期自动备份配置，再写一份恢复清单，存在账号之外。

卖家能借的：我们的规则、语气、闸门这些东西都是一点点调出来的，丢了很心疼，值得每周导出一份。

11. **Shop the King 的 Sam Baron：用 MCP 接 Helium 10，让 agent 管广告。**

Helium 10 官方博客写的案例：他们两个人管着上万个 SKU、六个渠道。agent 读 Helium 10 的数据，按 7 天、14 天、30 天三个窗口看广告，自动做关键词收割、否词、分时投放，他说这省下了以前每周一整天的活。

卖家能借的：多时间窗口一起看，比只看昨天的数据稳多了，不容易被一天的波动带着走。

12. **广告代理 Ramzan Malik：每天早上第一件事，看全店自然排名。**

同样是 Helium 10 的案例。他以前每周手动导出排名数据再丢给 AI 分析，要两三个小时；接上 MCP 以后，每天一条指令就能把 82 个 SKU 的排名、前 10 和 11–20 位的词都拉出来，再跟上期比。

卖家能借的：把“每天看排名”做成固定的早报，盯整个店，而不是只盯几个爆款。

13. **Anthropic 的 Project Vend：让 AI 真开一家小店。**

Anthropic 让 Claude 在办公室管一家自动售货小店。第一阶段问题不少：不查价就报价导致亏本卖，被人几句话就哄出折扣码，还编造过收款账户。第二阶段补了 CRM、能看到进货成本的库存系统，还专门不给它付款权限，采购前必须问人，情况才好转。另外他们的多智能体研究系统也是“一个主 agent 分派、多个子 agent 并行、最后专门核对引用”的结构。

卖家能借的：AI 犯错多半不是因为笨，而是看不到成本、没有闸门。给它看清楚成本和利润，花钱的事永远人来批。

**我接下来要做的**

别人的经验看看就好，我自己接下来就两件事：

* **把我已有的运营技能继续灌给团队。** 这十年攒下来的广告、Listing、选品、复盘的方法，一个一个做成技能交给对应的 Bot。我会的越多交给它们，它们就越像一个真正的运营团队。
* **把财务、风控、税务接上 AI。** 让财务和风控 Bot 自动对账、盯风险，再往前走到自动整理报税资料、跑 9810 出口退税的流程。涉及钱和申报的最后一步，还是我自己确认再提交。

这两块跑出结果，我再跟大家汇报。

# 领鹿🦌 SI Bot Agent Company OS

天机跨境旗下 · AI 原生公司组织与群体智能协作系统 · 总体方案 V1.0

我建议将“领鹿”定义为一个全新的产品方向：

不是再做一款 AI 聊天工具，也不是简单地把员工替换成 Bot，而是把一家企业的组织制度、岗位能力、业务流程、决策权限和管理机制，编译成一套可以持续运行的 AI 公司系统。

它有三个核心目标：

1. 组织数字化： 将公司、部门、岗位、职责、OKR、KPI、权限和 SOP 变成机器可以理解和执行的结构。
2. 业务智能化： AI 不只是执行命令，还能主动发现问题、跨部门调查原因、提出不同解决方案、预测结果和风险。
3. 能力资产化： 把员工及专家的经验、成功案例、决策依据和实际效果沉淀为企业能力，使组织可以持续改进，而不依赖某一个人的记忆或某一个模型。

你上传的基础版采用了“人类老板—幕僚长 Bot—四大职能部门—API/MCP 数据层”的结构，还强调了付款、改品、写操作等人工审批。这个基础方向可以保留，但要增加公司级治理、Agent 间协议、独立监督体系、持续学习和组织绩效管理。

# 领鹿🦌 SI Bot Agent Company OS

**AI 原生公司组织系统 · 立项方案 V1.0**

## 1. 产品愿景

领鹿不是单一智能体平台，而是将企业组织、业务能力、经营制度与人工智能融合的 Company OS。

产品的基本逻辑是：将人类公司的经营模型转化为智能体可以理解、执行、协同、监督和改进的软件架构。

系统不是简单复制人的岗位名称，而是复制岗位背后的职责、技能、知识、资源、操作权限和结果责任。

## 2. 企业组织对象模型

整个系统采用以下结构：

**Company → Business Unit → Department → Role Agent → Skill → Workflow → Task → Action → Outcome**

每个对象有独立的 ID、版本、权限、责任、负责人和绩效指标。

Company Agent 负责经营目标、跨部门协调与资源调度。

部门 Agent 对部门经营指标负责，岗位 Agent 对具体工作成果负责。

Skill 承担可复用的专业动作，Workflow 将多个 Skill 和 Agent 组合为业务流程。

## 3. 公司的 AI 部门

| 部门 | 核心职责 |
|----|----|
| AI CEO 与幕僚长 | 战略拆解、任务分派、资源协调、决策汇总 |
| 产品与市场部 | 选品、VOC、市场情报、竞品分析、产品开发 |
| 亚马逊经营部 | Listing、广告、转化率、自然流量、价格与购物车 |
| 供应链与财务部 | 采购、库存、履约、利润、现金流 |
| 技术与内容部 | 数据采集、系统研发、视觉、文案、多语言 |
| AI 监督审计部 | 权限审查、异常调查、风险阻断、业务质量 |
| AI 学习进化部 | 经验沉淀、知识更新、测试评估、技能升级 |

监督审计部独立于业务部门，不能由被审查的 Agent 自我授权。

## 4. 每个岗位的数字化责任合同

每个岗位使用标准 RoleSpec 配置，至少包括：

岗位 ID、使命、责任边界、业务对象、输入数据、标准输出、可用工具、不可执行事项、审批规则、交接对象、服务时限、OKR/KPI、记忆空间和质量评测。

例如：广告诊断 Agent 负责提出有数据依据的优化建议，但不能自行获得修改广告预算、价格或付款的权限。

## 5. 领鹿核心通信协议

建立内部 **Linglu Agent Contract（LAC）**，实现任务统一格式、跨岗位通信和权限传递。

每条 Agent 消息必须明确：

* 谁发起、谁负责、发给谁；

* 属于哪个企业、店铺、ASIN 和任务；

* 输入数据是什么、来源和时间是什么；

* 发现了什么事实，哪些还只是诊断假设；

* 建议什么动作、预计收益、存在什么风险；

* 需要什么权限、哪个人审批；

* 执行是否成功、实际经营效果如何。

Agent 之间可以串行、并行或协商执行，但最终操作必须受统一的策略与审批机制约束。

## 6. 业务问题的智能诊断机制

领鹿采用六步经营决策闭环：

**监测发现 → 数据核验 → 多部门诊断 → 方案推演 → 审批执行 → 效果复盘**

例如，当 Amazon ASIN 失去购物车或 Featured Offer 份额下降时：

价格 Bot 核查价格竞争力与利润底线；库存 Bot 核查可售库存；履约 Bot 核查配送承诺；竞品 Bot 核查其他报价；Listing Bot 核查链接状态；风控 Bot 核查账户问题。

系统综合输出多种解决方案、可验证证据、影响预测、失败风险及建议的执行顺序。

不允许未经完整诊断就默认建议降价。

## 7. AI 监督机制

所有动作分为观察、内部可逆操作、对外写入、高风险经营操作和法律/不可逆操作。

数据读取与内部计算可以在授权范围内自主执行。

首期系统中的价格、广告、Listing 等外部写入默认人工审批。

付款、采购、税务申报等高风险事项由明确授权的人类负责人把关。

每项执行均保留任务记录、审批记录、操作版本、数据来源和执行结果。

## 8. AI 学习与组织进化

领鹿建立两条循环：

**短期经营闭环：** 发现问题 → 采取行动 → 测量经营效果 → 纠正错误。

**长期知识闭环：** 观察员工与 Agent 操作 → 记录可审计的决策摘要 → 提炼案例 → 人工审核 → 测试验证 → 发布新 Skill/SOP。

所有知识版本必须可追溯、可回滚。

未经审核的运行轨迹不能直接变成新的生产规则。

## 9. 技术建设

前端采用 Next.js 与 TypeScript，构建企业经营工作台、组织图、Bot 岗位管理、任务中心和审批中心。

后端采用 Agent Runtime、工作流引擎、事件总线、权限引擎和统一数据服务。

数据层连接 Amazon SP-API、Ads API、ERP 和经过授权的第三方工具。

采用 PostgreSQL、对象存储、向量检索与业务指标数据库管理经营知识和业务事实。

引入 A2A、MCP 等标准的适配能力，同时保留领鹿自身的组织业务协议。

## 10. 第一阶段商业化落地

先从天机跨境真实运营场景开始，以亚马逊卖家作为首个行业模板。

初期部署七个关键岗位：幕僚长、店铺总管、广告诊断、库存预警、利润分析、购物车诊断和独立审计。

首批实现三个业务闭环：每日经营例会、购物车异常作战、广告健康诊断。

待内部验证后，形成可以复制到其他卖家的组织模板。

## 11. 商业模式

**SaaS：** 提供 AI 公司操作系统、行业岗位模板、工作流和连接器。

**GaaS：** 提供配置好的 AI 运营团队、专家监督和持续经营服务。

**Enterprise：** 提供私有部署、企业数据隔离、专属制度和定制化智能体组织。

长期目标是从单一亚马逊运营系统，升级到能够服务不同企业、不同行业、不同业务单元的 AI Company OS。

## 三、研发优先级与验收方式

第一期 · 12 周开发路径（建议）

1. 第 1–2 周：公司组织与制度内核

   RoleSpec、Company/Department/Agent 模型、权限分级、Agent 通信契约。
2. 第 3–4 周：业务数据底座

   亚马逊 API 与 ERP 只读接入、利润数据、任务日志、经营事件与数据追溯。
3. 第 5–7 周：三个完整业务流程

   每日经营例会、购物车异常诊断、广告健康诊断；实现 Agent 串联和并联。
4. 第 8–9 周：AI 监督与审批中心

   风险权限、人工审批、审计回放、重复操作阻断、故障恢复。
5. 第 10–12 周：学习与内部试运营

   真实案例回放、专家反馈、技能版本迭代、经营效果和使用成本评测。

验收不以 Bot 数量作为核心指标，而应该检验三个方面：业务结论是否可靠、整个流程是否能稳定运行、系统的经营建议是否真正创造价值。

## 四、领鹿如何与现有产品形成差异化？

亚马逊官方目前已经提供 Seller Assistant Workflows，能够执行定时任务、依据规则采取操作，并提供审批和审计能力；其官方帮助页面说明该 Workflows 功能目前面向美国店铺。

Amazon News+1

因此，领鹿的真正竞争壁垒不应该只是“AI 可以定时工作”。

它应当是：

企业级组织制度 + 跨部门经营智能 + 统一协作协议 + 专家知识资产 + 独立监督 + 长期学习闭环。

在技术上，标准化工具连接可以使用 MCP，跨独立智能体互操作可以采用 A2A，而企业内部的岗位、任务、审批和绩效语义需要由领鹿自己的业务协议来定义。

A2A Protocol+2

我认为这套系统最值得优先形成自主资产的，是 Linglu Core（公司运行内核）、RoleSpec（岗位合同）、LAC（组织通信协议）、Evaluation（企业能力评测体系） 四个模块。

这四个模块决定了领鹿未来是一套只能用于亚马逊运营的 Bot 工具，还是可以持续扩展成跨境电商乃至其他行业的真正 AI 原生公司基础设施。
