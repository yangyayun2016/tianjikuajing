上一篇写了 [@poteto](https://x.com/poteto) 的 30x 发码与 `/statechart`，很多人会把「状态机 + TLA+」听成「形式化一上，bug 就没了」。她随后发了一条长帖专门降温：[原帖](https://x.com/poteto/status/2118416074601545968)。

核心一句话：**形式化再看好，也不能证明代码没有 bug，只能证明在特定假设下符合 spec；而 spec 对不对，仍然靠人判断。**

下面按「她说了什么 → 三类工具怎么取舍 → `/statechart` 还值不值 → 我们怎么落地」整理一版笔记（以 2026-11-05/06 公开内容为准）。

## 1. 形式化在证什么、不证什么

她自己说对形式化相当 bullish，但建议大家自己做功课（并标明：她不是形式化专家）。边界写得很清楚：

- **能证的**：在一组假设下，实现与规格一致；
- **不能证的**：规格本身写对了、业务意图对了、线上环境与假设一致、实现之外的一切。

所以「过了模型检查 / 定理证明」≠「上线没 bug」。它最多把「实现是否偏离了我们写下的规则」这件事做硬；规则写歪了，证明只会更用力地把歪规则钉死。

对带 agent 的团队，这其实是好事：别把银弹期待押在 TLA+/Lean 上，也别因为「证不全」就丢掉形式化——它本来就不是万能钥匙。

## 2. 验证拆成三层，别指望一层打通关

她把验证拆成大致三层，按场景叠加，而不是二选一：

**① 约束与护栏（Constraints / Guardrails）**  
类型系统、lint、API 契约、权限边界、字段字典。便宜、可进 CI、agent 和人都能立刻踩到。这是跑道上的护栏，不是终点验收。

**② 经验验证（Empirical）**  
测试、eval、真实环境实跑、报表回读。能抓到「假设外」和「交互后才出现」的问题。贵一点，但贴近真实。

**③ 形式化（Formal）**  
按问题选工具，而不是先选信仰：

| 方向 | 代表 | 适合什么 | 代价 / 风险 |
| --- | --- | --- | --- |
| 规格 + 模型检查 | TLA+ / TLC | 端到端性质、并发与状态机；少写验证码 | 规格与代码可能漂移，宜配实跑 |
| 定理证明 | Lean / Dafny | 想覆盖「全输入」的强保证 | 贵、门槛高 |
| 有界模型检查 | CBMC / Kani | 直接对着真码查有限步 | 步数有界，不是无限保证 |

近中期现实做法是**分层叠加**：护栏挡傻错，经验验抓漂移与实况，形式化盯关键状态与「理论上不该发生」的路径。

## 3. `/statechart` 的主价值：缩小审查面，核对意图

她用 Tibo.dog story mode 的状态图举例：同一套有限状态机上，TLA+ 标出了多处真实 bug（加载卡住、幕后动画、自动选牌指到旧手牌、暂停盖住台词等）。图不是装饰，而是把「可能状态 × 可能迁移」摊开，让审查面变小。

所以 `/statechart`（配合 TLA+）的主价值不是「证明完美」，而是：

1. **强迫把意图写成状态与迁移**——agent 是否真懂目标，一看就穿帮；
2. **缩小人要审的表面**——只盯关键状态、不可逆动作、错误回退；
3. **给形式化一个落脚点**——先有清晰状态机，再谈模型检查有没有意义。

她还补了一刀：即便将来「苦涩教训」路线能打出近乎完美的代码，**意图对齐仍然需要 statechart 这类东西**。代码写对了，也可能写的是错需求。

上一篇说过：agent 最常见的失败不是「不会写」，而是「目标理解偏了还写得很顺」。这条长帖把那句话钉死了。

## 4. 和上一篇怎么接上

| 上一篇 | 这一篇补上的刹车 |
| --- | --- |
| 先修跑道再放飞机（agent-friendly 架构） | 跑道上的检查分三层，别只迷信形式化 |
| `/statechart` 核对 agent 是否懂目标 | statechart 缩审查面；形式化证的是 spec，不是业务直觉 |
| 合并前 agent 自检 + 确定性 CI | 自检/CI ≈ 护栏 + 经验；形式化留给关键状态机 |
| 少对抗式抽象 review，多实测 | 实测就是经验层；形式化不能替代它 |

## 5. 对天机跨境 SI Bot 的落地建议

我们不需要立刻上 Lean 全仓证明。更划算的是：

1. **广告健康 / 关键词打标 / 托管流水线：先画状态机**  
   有哪些状态（待诊、待批、已改价、已回读）、谁能迁移、哪些不可逆、出错退哪。这就是 `/statechart` 的业务版。

2. **护栏写进 skill / 仓库 / CI**  
   字段字典、红线规则、出价上下限、禁止动作列表——让 agent 踩得到，而不是靠人反复口头纠正（对齐她的 `/correct` 思路）。

3. **经验层用报表回读与干跑**  
   改出价、改预算、关广告：以后台指标与规则引擎回读验收，少做空口 review。

4. **形式化只砸关键路径**  
   例如「不可售移除 → 重入仓」「Pan-EU 同步 → 配送费变化」这类状态多、并发/时序容易错的流程，再考虑 TLA+ 或有界检查；不要为了形式化而形式化。

5. **人只批意图与高风险**  
   spec / 状态机对不对、钱与合规相关动作——留给人；实现是否符合已写下的规则——尽量交给护栏、回读与（必要时）模型检查。

## 小结

@poteto 这轮不是在劝退形式化，而是在**校正期待**：形式化很有用，但它证明的是「符合我们写下的规则」，不是「世界上没有 bug」。验证要分层；`/statechart` 仍然值得做，因为它先解决意图对齐，再谈证明。

对跨境 SI Bot 团队：先把状态机和护栏写清楚，再用回读验收，关键路径再上形式化——比空谈「我们要用 TLA+」更接近她真正在推的做法。
